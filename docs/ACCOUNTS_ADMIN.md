# Beta administration and player account plan

Research checked 2026-11-02. The current service accepts a signed EOA wallet and derives a stable, 19-character Luanti protocol name from its address. It has admin stats, a recent native player explorer, local username holds and an optional wallet-bound beta invite gate. Player signup usernames, ZeroDev and card payment remain unimplemented. Keep the internal character key stable while adding public display names; changing the native key would risk inventories, protection and town ownership.

## Signup choices and account identity

1. **Existing Ethereum wallet:** keep the current nonce/domain/chain-bound Sign-In with Ethereum challenge. After sign-in, let the player select a verified ENS name they control; retain the wallet-derived fallback if they do not own one. The wallet address is the account key; the ENS name is a mutable display alias. An ENS address record pointing at a wallet, or a reverse name, is not by itself proof that the wallet **owns** that ENS name. Verify current ownership/control through the applicable ENS registry path before binding an alias, then recheck after transfer/expiry and on later login. Normalize ENS names with the current ENS rules and prevent two MineMine accounts from claiming the same displayed name. The existing forward-verified reverse lookup is useful for a primary-name suggestion, but does not satisfy the “any ENS name they own” request. A new server verifier now checks exact ENSv2 ownership and active ENSv1 `.eth` registrar/NameWrapper ownership against mainnet; its read-only `vitalik.eth` registrant/manager distinction passed. Name selection and display are the next integration step; ENSv1 DNS-import expiry is not yet supported. [ENS ownership and wrapping](https://docs.ens.domains/wrapper/states/) and [ENSv2 readiness](https://docs.ens.domains/web/ensv2-readiness/) make the ownership API a versioned implementation decision.
2. **ZeroDev embedded wallet:** the [current ZeroDev Wallet docs](https://docs.zerodev.app/wallets) describe passkey, social or email authentication that provisions a smart account. This gives the requested conventional, non-extension signup experience, although the resulting account is still an on-chain wallet. These players choose a unique custom MineMine username. ZeroDev's [quickstart](https://docs.zerodev.app/wallets/quickstart) distinguishes EIP-7702 mode, which exposes a user wallet address, from ERC-4337 mode, which exposes a Kernel smart-account address. The MineMine backend now checks deployed [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271) and undeployed [ERC-6492](https://eips.ethereum.org/EIPS/eip-6492) signatures through a matching-chain RPC before issuing a session or game grant; its local-Anvil HTTP proof, including a forged-wrapper denial, passed [foundation run 41390601122](https://github.com/cupOJoseph/minemine/actions/runs/41390601122). A real ZeroDev project and browser account still need end-to-end QA. ZeroDev's [signing guide](https://docs.zerodev.app/smart-accounts/sign-and-verify) recommends the same distinction. Test exact account continuity, logout/revocation and MINE/town transactions before enabling this option.
3. **Credit-card scope:** the product now calls for a **$2 USD `username.minemine.eth` reservation during the conventional signup path**. The project owner reports owning `minemine.eth` and chose a MineMine-managed resolver record pointing at the player's ZeroDev wallet, rather than a transferable subname token. This is a player charge, separate from ZeroDev's provider usage bill. ZeroDev's [wallet docs](https://docs.zerodev.app/wallets) describe app-side usage credits; its [smart routing address](https://docs.zerodev.app/onramp/smart-routing-address) is a separate fiat-onramp concept. Use a hosted payment provider and verified server-side fulfillment for the name reservation. It is not yet specified whether account signup has any additional price. Do not collect card numbers in MineMine or enroll in a paid provider plan until the test flow and budget are reviewed. The existing $10/month cap is for the first DigitalOcean host, not proof that payments, ZeroDev or ENS transactions fit it.

Custom MineMine usernames for the ZeroDev signup path and wallet users need **one server-owned registry**, so a card buyer and a verified ENS wallet cannot both claim the same bare MineMine handle. Store normalized handles, account ownership, checkout holds, paid reservations and audit history outside the web root, and back them up with the world. A wallet may still display its full verified ENS name when its bare label is unavailable. The native character's wallet-derived identifier remains the authorization key. Name changes must update display in the web UI and native nametag without changing inventories, player files or town ownership. A code or name reservation must not by itself prove wallet or ZeroDev identity. The detailed [paid-name and collision design](PAID_NAMES.md) covers the `$2` checkout, `minemine.eth` control gate, managed-name rights and failure states.

## Admin dashboard

The `/api/admin/stats`, name-reservation and beta-code routes check the existing signed-wallet session against `ADMIN_WALLET_ADDRESSES` on every request; the empty default allows nobody. They inherit the service's per-IP rate limit and no-store policy. Creating or releasing a seven-day name hold, or creating or revoking a code, additionally requires a signature from the last five minutes. Each transition is written to its private SQLite audit table. Grant writes and an audit-history UI remain. A hidden navigation link is insufficient authorization. Keep admin secrets outside the public bundle. Future smart-account admins need the same contract-signature validation as players before being allowlisted.

**Metrics:** the first implementation writes native join logs by UTC month and an atomic current-player snapshot from the wallet-auth mod. `/api/admin/stats` reads only a fresh snapshot while the native heartbeat is live and counts distinct stable character IDs with at least one accepted join in the current UTC day, Monday-start week and calendar month. It returns the period starts and earliest scanned join. Browser sessions and page views do not count. Unit tests cover UTC boundaries, deduplication and stale presence. Native run [41331833005](https://github.com/cupOJoseph/minemine/actions/runs/41331833005) passed two browser wallets in the world and saved a real snapshot with two daily/weekly/monthly active characters and one currently connected. Later work must add retention/rotation, long-world measurement and a clear collection-start marker before presenting lifetime statistics.

**Player explorer:** the first `/api/admin/players` endpoint searches stable character IDs only, with 25-row server pagination and a rolling 12-month accepted-join window. It shows first and last join within that window and count, without wallet addresses or private grants. Search by MineMine username and verified ENS alias, account type, public name, current/last-seen status and town membership require the future account/profile index. Keep private grants, full wallet addresses, balances and purchase details out of the default view unless an explicit admin need is established. Verify that a regular player cannot query another player's private record.

**Beta codes and reserved names:** the admin can create a code with a 1–30 day expiry, 1–100 total uses and optional intended wallet address; list uses and revoke it. The 192-bit secret is shown only in the creation response and stored as a SHA-256 hash. A signed wallet redeems it atomically into a durable account admission; repeating redemption for the same account does not consume another use. Revoking a code stops new redemptions but does not eject players already admitted. The private audit tables record name and invite transitions. The admin-only `/api/admin/audit` and dashboard show the latest 50 combined events with item ID, action, actor and UTC time, never an invite secret. Admission revocation remains. The admin's name reservations, card-checkout holds and verified ENS handle claims use the **same atomic name registry**. Admin name holds have a seven-day expiry; assigning a reserved name to a specific future account still needs UI and identity work. Tests cover code expiry, revocation, limits, collision, case folding, restart, and access boundaries. `BETA_INVITES_ENABLED` defaults off; when enabled, the game-ticket and WSS bridge require an admission or allowlisted admin wallet. The solo playtest remains accessible. Browser and remote-host rehearsal remain before enabling the gate publicly.

## Delivery order

1. Verify the owner's reported control of `minemine.eth` and its managed-record write permissions; settle the managed name's duration and whether the `$2` covers only the name or also the account. Pick the ZeroDev account mode. Review current provider limits and costs; use only test projects for the first integration.
2. Add durable native presence events and UTC active-player aggregates; build read-only admin metrics against a disposable world and exercise restarts.
3. Add admin authorization, audit log, beta-code lifecycle and a durable normalized username/reservation registry; test concurrent redemption and name claims.
4. Add the wallet signup screen with verified ENS ownership selection and transfer/revocation handling. Keep native IDs unchanged. Add custom username selection for ZeroDev accounts.
5. Add ZeroDev signup and smart-signature verification, then test a funded testnet account's MINE transfer and paid town claim. Implement hosted `$2` name checkout, verified idempotent fulfillment and ENS issuance only after parent control, rights, duration and refund rules are settled.
6. Build the player explorer and admin dashboard UI on top of tested APIs; verify non-admin denial, mobile layout, accessibility and production-data migration/backup behavior.

`/admin.html` renders current and UTC day/week/month counts, current stable character IDs, a freshness warning and the recent player explorer from allowlisted APIs. It has controls to create/release seven-day local name holds and create/list/revoke beta codes. The wallet panel accepts a code for the current signed-in address when invite mode is enabled. An admin signs in with the configured wallet on the main page first; the empty allowlist grants nobody. [Native run 41374795081](https://github.com/cupOJoseph/minemine/actions/runs/41374795081) passed a mocked-API Chromium desktop/mobile smoke for the new admin controls, including create, release and revoke interactions, with screenshots in the run artifact. The player invite form still needs browser interaction QA. No player name checkout or ZeroDev API is exposed by the current build.
