# Beta administration and player account plan

Research checked 2026-11-01. The current service accepts a signed EOA wallet and derives a stable, 19-character Luanti protocol name from its address. It has no beta-code, username, ZeroDev, card-payment, or admin-dashboard implementation yet. Keep the internal character key stable while adding public display names; changing the native key would risk inventories, protection and town ownership.

## Signup choices and account identity

1. **Existing Ethereum wallet:** keep the current nonce/domain/chain-bound Sign-In with Ethereum challenge. After sign-in, let the player select a verified ENS name they control; retain the wallet-derived fallback if they do not own one. The wallet address is the account key; the ENS name is a mutable display alias. An ENS address record pointing at a wallet, or a reverse name, is not by itself proof that the wallet **owns** that ENS name. Verify current ownership/control through the applicable ENS registry path before binding an alias, then recheck after transfer/expiry and on later login. Normalize ENS names with the current ENS rules and prevent two MineMine accounts from claiming the same displayed name. The existing forward-verified reverse lookup is useful for a primary-name suggestion, but does not satisfy the “any ENS name they own” request. [ENS ownership and wrapping](https://docs.ens.domains/wrapper/states/) and [ENSv2 readiness](https://docs.ens.domains/web/ensv2-readiness/) make the ownership API a versioned implementation decision.
2. **ZeroDev embedded wallet:** the [current ZeroDev Wallet docs](https://docs.zerodev.app/wallets) describe passkey, social or email authentication that provisions a smart account. This gives the requested conventional, non-extension signup experience, although the resulting account is still an on-chain wallet. These players choose a unique custom MineMine username. ZeroDev's [quickstart](https://docs.zerodev.app/wallets/quickstart) distinguishes EIP-7702 mode, which exposes a user wallet address, from ERC-4337 mode, which exposes a Kernel smart-account address. The current MineMine verifier only recovers EOA signatures. For 4337, verify contract signatures under the SIWE message's chain ID with [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271), including [ERC-6492](https://eips.ethereum.org/EIPS/eip-6492) for an undeployed account, before issuing a MineMine session or game grant. ZeroDev's [signing guide](https://docs.zerodev.app/smart-accounts/sign-and-verify) recommends the same distinction. Test exact account continuity, logout/revocation and MINE/town transactions before enabling this option.
3. **Credit-card scope:** ZeroDev's current documentation says the **app** consumes usage credits for signatures and transactions, with a free testnet tier and paid overages; it does not establish that every player must pay by card to create a wallet. Its [smart routing address](https://docs.zerodev.app/onramp/smart-routing-address) can receive funds from a separate fiat onramp, which is a different product flow. Clarify whether the intended card charge is MineMine signup revenue, a player fiat purchase, or the project's ZeroDev bill. Do not request card data in MineMine or enroll in a paid plan until the product, payment provider and budget are decided. The existing $10/month limit is for the first DigitalOcean host, not evidence that ZeroDev or a payment processor fits it.

Custom MineMine usernames for the ZeroDev signup path need a server-owned registry: one normalized, unique handle per account; a clearly documented character set and length; a separate display label if desired; atomic claim/release/rename rules; reserved words; abuse/moderation policy; and an audit trail. Store the registry outside the web root and back it up with the world. The native character's wallet-derived identifier remains the authorization key. Name changes must update display in the web UI and native nametag without changing inventories, player files or town ownership. A code or name reservation must not by itself prove wallet or ZeroDev identity.

## Admin dashboard

The first read-only `/api/admin/stats` route checks the existing signed-wallet session against `ADMIN_WALLET_ADDRESSES` on every request; the empty default allows nobody. It inherits the service's per-IP rate limit and no-store policy. Build the future admin-only area with fresh reauthentication for writes and an audit record for grants, reservations and code changes. A hidden navigation link is insufficient authorization. Keep admin secrets outside the public bundle. Future smart-account admins need the same contract-signature validation as players before being allowlisted.

**Metrics:** the first implementation writes native join logs by UTC month and an atomic current-player snapshot from the wallet-auth mod. `/api/admin/stats` reads only a fresh snapshot while the native heartbeat is live and counts distinct stable character IDs with at least one accepted join in the current UTC day, Monday-start week and calendar month. It returns the period starts and earliest scanned join. Browser sessions and page views do not count. Unit tests cover UTC boundaries, deduplication and stale presence; the updated native browser CI test is still a gate. Later work must add retention/rotation, long-world measurement and a clear collection-start marker before presenting lifetime statistics.

**Player explorer:** search by MineMine username, verified ENS alias or stable character ID; show current/last-seen status, account type, public name, join history and town membership with pagination. Keep private grants, full wallet addresses, balances and purchase details out of the default view unless an explicit admin need is established. Verify that a regular player cannot query another player's private record.

**Beta codes and reserved names:** allow an admin to create a code with expiry, usage limit and optional intended account; list remaining uses; revoke it; and inspect redemption audit history. Store only a hash of the secret code, present the plaintext once, and redeem atomically so parallel requests cannot exceed the limit. Reservation records need a normalized username, intended account or expiry, creator, reason and audit trail. A later successful identity proof can claim a reserved name; unclaimed reservations expire. Test collisions, case folding, restart, abuse limits and admin/regular-player access boundaries. The invite gate should apply before issuing a playable native grant once the beta opens, without disabling the existing solo mode.

## Delivery order

1. Pick the signup/card interpretation and ZeroDev account mode. Review current ZeroDev project limits and costs; use only a no-charge test project for the first integration.
2. Add durable native presence events and UTC active-player aggregates; build read-only admin metrics against a disposable world and exercise restarts.
3. Add admin authorization, audit log, beta-code lifecycle and a durable normalized username/reservation registry; test concurrent redemption and name claims.
4. Add the wallet signup screen with verified ENS ownership selection and transfer/revocation handling. Keep native IDs unchanged. Add custom username selection for ZeroDev accounts.
5. Add ZeroDev signup and smart-signature verification, then test a funded testnet account's MINE transfer and paid town claim. Add any card checkout only after the payment requirement and provider are explicitly settled.
6. Build the player explorer and admin dashboard UI on top of tested APIs; verify non-admin denial, mobile layout, accessibility and production-data migration/backup behavior.

The read-only `/admin.html` page renders current and UTC day/week/month counts, the current stable character IDs and a freshness warning from the allowlisted stats API. An admin signs in with the configured wallet on the main page first; the empty allowlist grants nobody. Desktop and mobile layouts passed local visual QA with a mocked API response. No player explorer, beta-code, reservation or ZeroDev API is exposed by the current build.
