# Native world load measurements

This is instrumentation for the first shared MineMine world. It does **not** establish a player capacity or make the world public. The snapshot is written by the wallet-auth mod to `minemine-native-metrics.json` inside the private world directory roughly every ten seconds. `WORLD_DIR=/srv/minemine/world npm run metrics:native` checks its schema and freshness, then prints it. Keep the file outside the web root.

## What the numbers mean

| Field | Meaning |
| --- | --- |
| `online_players` | Luanti's count of connected player objects when the snapshot was written. |
| `samples`, `sample_seconds` | Server-step samples and their total elapsed time in this roughly ten-second window. |
| `step_interval_ms_mean`, `p50`, `p95`, `p99`, `max` | Elapsed milliseconds **between** globalstep callbacks, including scheduling and other work. A long interval can signal lag; it is not CPU execution time for one callback. |
| `server_max_lag_ms` | Luanti's built-in current maximum lag, when available. Its internal window is separate from the sampled percentiles. |
| `observed_at` | Unix timestamp in seconds. The checker rejects a file older than 30 seconds. |

[Luanti's API](https://api.luanti.org/core-namespace-reference/) defines `register_globalstep`'s `dtime` as time since the last server step and exposes `get_server_max_lag()` separately. Its [timing guide](https://docs.luanti.org/for-creators/api/timing-and-event-loop/) warns that expensive globalstep work can block the server thread. MineMine only collects one number per step and sorts/writes the small window periodically. The first production rehearsal must still measure whether that work has a material cost.

## Four-client CI rehearsal

The native workflow temporarily copies its config with `max_users = 4` for the disposable test world; the checked-in two-player alpha config is unchanged. After the two-wallet protection test, `test/integration/browser-native-load.mjs` signs in four distinct disposable wallets and keeps their real browser engines connected, first at two and then at four. It requires two fresh native snapshots at each stage and saves them with the server/Node memory series in the workflow artifact. The browser processes run outside the 1 GiB server/Node service limit.

[Native run 41579632572](https://github.com/cupOJoseph/minemine/actions/runs/41579632572) passed all jobs. Its retained snapshots reported two, two, four and four online players. The four-player windows had 91.35 and 91.14 ms p95 step intervals. The Luanti/Node service cgroup peaked at 265,560,064 bytes with zero OOM kills. Individual browser join times were 10.1, 18.2, 48.7 and 68.9 seconds; the later joins are a concern even though the short server-step windows stayed near 90 ms. This one CI runner and already-edited test world do not prove a four-player public capacity or a 16-player scale result. Browser resource use, sustained edits, remote latency and reconnect behavior at four players were not measured.

The native log records 2, 8, 30 and 40 seconds between the four clients' new-connection and joined-game lines, respectively. The first two timings are also affected by one-second log precision. The browsers share the same CI runner CPU even though they sit outside the server memory cgroup. The timing rehearsal records wallet challenge/verify, document load, ticket response, game-proxy opening and native connection-to-join separately in `native-load-joins.jsonl`; these timings locate the slow phase without guessing at a server setting. A separate-client-host run is still required to remove CI browser CPU contention from the server capacity measurement.

[Timing run 41581463747](https://github.com/cupOJoseph/minemine/actions/runs/41581463747) passed and retained the new join-phase file. Ticket responses arrived 4.2, 5.9, 11.7 and 7.3 seconds after each client's page navigation, while Luanti connection-to-join took 2, 17, 82 and 90 seconds. Total join times were 8.1, 30.1, 125.8 and 158.1 seconds. Its two four-player snapshots again had about 91 ms p95 step intervals, and the 1 GiB server/Node cgroup peaked at 250,056,704 bytes with zero OOM kills. This isolates a large delay after the browser opens its game proxy, including the native connection-to-join phase; it does not prove whether the cause is client CPU contention, transport reliability, map delivery or another handshake cost. Test with clients on separate hardware and collect per-process CPU and network traces before changing world limits.

[Separate-process run 41673320789](https://github.com/cupOJoseph/minemine/actions/runs/41673320789) launched each disposable client in its own Chromium process with the same four-player world, timing fields and server memory limit. All jobs passed. Total joins took 8.1, 10.1, 12.1 and 16.2 seconds; native connection-to-join took 2, 3, 3 and 5 seconds. Two four-player snapshots had 91.11 and 91.17 ms p95 step intervals. The 1 GiB server/Node cgroup peaked at 279,097,344 bytes with zero OOM kills. This is much faster than the four-context runs and makes shared-browser scheduling a plausible contributor. The runs used different CI runners and time windows, so the comparison does not establish causation. All clients still shared their CI runner's CPU; separate client hardware, sustained edits and sixteen-player load remain the capacity gate.

The [combined shared-process run 41848584950](https://github.com/cupOJoseph/minemine/actions/runs/41848584950) timed out waiting 180 seconds for its fourth native join. The third joined in 87.7 seconds. The retained native log shows the fourth wallet connected at 14:46:18 UTC and requested media was sent at 14:47:28, but no join marker appeared before the 14:48:13 timeout. This is a failed four-online check, even though three players joined. The [separate-process run 41849042959](https://github.com/cupOJoseph/minemine/actions/runs/41849042959) passed on the same code base with four joins in 6.1, 8.1, 8.1 and 10.1 seconds, two four-online snapshots near 91 ms p95 step interval, and a 277,131,264-byte peak with zero OOM kills in the 1 GiB service slice. These runs do not isolate server capacity from browser or runner contention; external clients on independent hardware remain necessary.

## Eight-client CI rehearsal

[Native run 41680083138, attempt 2](https://github.com/cupOJoseph/minemine/actions/runs/41680083138/attempts/2) passed the full two-wallet protection, eight-client load, restart, map and host-archive sequence on code commit `a8a3c89`. The disposable world alone used `max_users = 8`; the checked-in alpha config still caps two. Eight distinct signed wallets joined through eight separate headless Chromium processes and remained online for two fresh native metrics windows. Their total page-navigation-to-native-join times were 8.1, 10.1, 12.1, 16.1, 20.2, 22.2, 26.2 and 34.2 seconds. Native connection-to-join intervals were 2, 3, 4, 5, 6, 6, 8 and 11 seconds at one-second log precision. The two eight-player windows had 91.06 and 90.99 ms p95 step intervals, each covering about ten seconds. Luanti and Node peaked at 282,673,152 bytes inside their 1 GiB zero-swap cgroup, with zero `memory.events max`, OOM and OOM-kill events. The sampled sum of their RSS peaked at 320.6 MiB; cgroup and RSS figures use different accounting and should not be added.

Attempt 1 failed **before** the load script: the existing browser protection smoke did not observe its synthetic dig result while its screenshot showed the target stone and the native server reported no OOM event. The unchanged rerun passed. This is a reliability concern for the prerequisite smoke, not evidence of an eight-player failure. The passing run used one CI machine for all browser processes and a short, mostly idle world. It did not measure sustained edits, reconnects at eight, separate-client hardware, whole-VM OS/Caddy memory, CPU utilization or egress. These results justify the next external load test; they do not establish a public eight-player cap or the 16-player milestone.

The [final-head eight-client run 41683908512](https://github.com/cupOJoseph/minemine/actions/runs/41683908512) also passed. Its two eight-player windows were 91.23 and 91.20 ms p95, and its Luanti/Node cgroup peaked at 263,983,104 bytes with zero max or OOM events. The eighth join took 52.3 seconds, versus 34.2 seconds in the earlier passing run. This variation reinforces the need for separate client hardware and repeated runs before setting a public cap.

## Sixteen-client CI join rehearsal

[Native run 41686780474](https://github.com/cupOJoseph/minemine/actions/runs/41686780474) passed on test-code commit `34e593e`. The disposable world used `max_users = 16`, and Luanti plus Node shared a verified 1 GiB, zero-swap, one-vCPU cgroup. Sixteen distinct signed wallet characters joined through separate headless Chromium processes. Two fresh roughly ten-second windows each reported **16 online** and p95 step intervals of **91.38 and 91.44 ms**. The last client joined 42.3 seconds after page navigation; across all sixteen, joins ranged from 8.1 to 42.3 seconds and native connection-to-join from 2 to 17 seconds. The service cgroup peaked at **271,024,128 bytes**, with zero memory-limit or OOM events. Its CPU counter recorded 17 throttled periods out of 6,139, totaling 626,347 microseconds; the quota file was `100000 100000`. These are service-slice observations, not whole-VM utilization.

The same CI run also passed the prerequisite two-wallet protection smoke and the later restart, map export and host-archive checks. The 16 clients were mostly idle and all ran on the same CI machine outside the service slice. The operating system, Caddy, VM disk growth and public network were not inside the measured cap. Movement, block edits, town denial, egress, repeated joins and reconnects **while sixteen remain online** are still required on a named host with separate client hardware. This run proves a short 16-browser join and presence result under the stated service limits; it does not establish a production 16-player cap or a need to begin SpacetimeDB migration.

[Reconnect run 41693124148](https://github.com/cupOJoseph/minemine/actions/runs/41693124148) passed on test-code commit `b8d13e4`. After 16 distinct wallet characters joined, the harness closed the last browser and checked both a fresh **15-online** native metrics snapshot and the exact 15-name private presence set. It then signed the same wallet in again, required its original native character name and a new native connection/join marker, and checked the restored exact 16-name set and a fresh **16-online** snapshot. The returning browser took **60.9 seconds** from navigation to join, including **24 seconds** from native connection to join. The two initial 16-player windows were 91.20/91.32 ms p95; the 15-player and restored 16-player windows were 91.17/91.08 ms p95. The one-vCPU Luanti/Node cgroup peaked at 264,265,728 bytes with zero memory-limit or OOM events, and recorded 43 throttled periods out of 9,254. This verifies one local reconnect under 15 other idle browser clients. It does not cover repeated reconnects, edits during reconnect or separate client hardware.

## Browser-observed game traffic

[Native run 41701603051](https://github.com/cupOJoseph/minemine/actions/runs/41701603051) counted frame payload lengths on each Chromium `game-proxy` WebSocket, without recording frame contents. All 16 signed clients joined, the 15/16 reconnect check passed, and the one-vCPU Luanti/Node cgroup peaked at 266,997,760 bytes with zero memory-limit or OOM events. At the first 16-online snapshot, cumulative server-to-browser game WebSocket payload was 40,863,875 bytes and browser-to-server payload was 3,223,082 bytes across all clients since their individual connections opened. During the next **10.05-second** interval with 16 mostly idle clients, those totals grew by **35,863 bytes outbound** and **9,299 bytes inbound** (256 and 242 frames). This is one short post-join interval; some map delivery may still have been in progress. It is not a steady-state rate to multiply into a monthly bill.

These counts exclude HTTP/WASM downloads, WebSocket framing, TCP/IP and TLS overhead, Caddy, retransmissions and a public-network route. Browser clients and the operating system were outside the measured server slice. Measure actual VM interface egress and game activity on the named host before using a traffic forecast for the $10 alpha plan.

## Sixteen-client movement rehearsal

[Native run 41705481883](https://github.com/cupOJoseph/minemine/actions/runs/41705481883) passed on movement test commit `ea666a8`. After all 16 signed browser clients joined, a disposable server mod captured each native player's position before and after eight browser canvases received directional key presses for eight seconds. The native snapshot still counted **16 online**, and **5 of 8** actors moved at least half a block horizontally. Their horizontal displacements were 32.23, 2.51, 0, 0.23, 31.75, 2.51, 0 and 1.22 blocks. The test required at least two movers so that a blocked spawn or headless input on one client would not mislabel the whole run, but the three near-stationary actors need investigation before an active-player capacity claim.

The two fresh pre-movement 16-online native windows measured **91.55 and 91.16 ms p95** globalstep intervals; the fresh movement observation measured **90.93 ms p95**. Browser-observed game WebSocket payload increased by **214,704 bytes server-to-browser** and **48,259 bytes browser-to-server** from the movement baseline through the post-movement sample, including canvas focus and sampling time. It is not a fixed-duration steady-state traffic rate. The Luanti/Node one-vCPU, 1 GiB, zero-swap cgroup peaked at **275,345,408 bytes**, with zero memory-limit and OOM events and 24 throttled periods out of 8,246. The slowest initial browser join took 40.4 seconds; the later same-wallet reconnect took 103.6 seconds. The reconnect restored the exact 16-player set.

All browser processes shared one CI runner outside the server slice. This short movement check did not exercise block edits, town denials, sustained traversal, Caddy, whole-VM memory or public network egress. Repeat from separate client hardware on the named host before changing the two-player alpha cap or starting a SpacetimeDB migration.

## Opt-in 32-client rehearsal and movement-fixture correction

The native workflow now accepts a manual 32-client input while routine PR CI remains at 16. [Manual run 41894150488](https://github.com/cupOJoseph/minemine/actions/runs/41894150488) did not reach 32. Fifteen separately signed Chromium clients joined; the 16th connected and was offered 567 compressed media files but did not reach a native join within the 180-second deadline. Join time grew from 28.2 seconds at client 4 to 172.3 seconds at client 15. Two fresh eight-player windows measured 91.34 and 91.73 ms p95 step intervals. The Luanti/Node one-vCPU, 1 GiB service slice peaked at 266,764,288 bytes and recorded zero memory-limit and OOM events. The test did not capture browser memory or CPU outside that slice, so the failure does not establish a native server limit or a SpacetimeDB requirement. A 32-online snapshot, movement window and reconnect were never reached.

A [second opt-in 32-client run 41911907967](https://github.com/cupOJoseph/minemine/actions/runs/41911907967) used the separate browser-runner sampler but ended with GitHub's `cancelled` conclusion at the 50-minute job timeout. The browser-wallet/load step was still active. GitHub retained neither its log nor a measurement artifact, so this run cannot establish how many clients joined or whether browser, service, or whole-runner resources caused the delay. The workflow now gives optional 32-client load a 25-minute step deadline, leaving time for its EXIT trap and always-run artifact upload before the job limit. Routine 16-client CI keeps its previous behavior.

[Exact-head bounded run 41921691547](https://github.com/cupOJoseph/minemine/actions/runs/41921691547) verified that retention path: the optional 25-minute load deadline ended the job's gameplay step with a failure result, but the always-run artifact saved join, runner, native and cgroup measurements. Join time grew from 6.1 seconds for client 1 to 103.8 seconds for client 16 and 151.8 seconds for client 20. Two fresh 16-online windows measured 91.85 and 91.15 ms p95 server-step interval. The final retained native snapshot reported 20 online with 91.00 ms p95 over its last 10.05-second window, but the load script did not reach a 32-online stage or its movement/reconnect checks.

The one-vCPU, 1 GiB Luanti/Node service cgroup peaked at 273,670,144 bytes and recorded zero `max`, OOM and OOM-kill events. Its maximum **summed process RSS** was 18.58 GiB, which double-counts shared pages and cannot be interpreted as physical memory use. The runner's browser CPU and whole-VM deployment behavior were not measured. These observations do not identify the cause of progressively slower serial browser joins or establish a native 20-player cap. ## First capacity rehearsal

On a named test host, record the exact Luanti build, world seed/size, view-distance settings, host plan, CPU and RAM limit, client hardware/browser, and network location. Keep clients outside the server's resource limit. Collect snapshots at idle and during a staged 2, 4, 8 and 16-client run, with joins, movement, block edits, town-protected edit denials and reconnects. Preserve a timestamped series of the snapshots, native log, service CPU/RAM, disk growth and network egress. Record successful joins, edit visibility, disconnects and reconnect time. A two-client short smoke test cannot be extrapolated to sixteen players.

The first $10/month host is sized only for the invite-only two-player alpha. Compare the measurements with client-visible delay and resource headroom before setting an acceptable player cap or changing the host budget. If server-step intervals or max lag rise sharply, a separate SpacetimeDB process cannot by itself make Luanti's world simulation faster; use the [scaling plan](SPACETIMEDB.md) to choose which state, if any, should move after the native baseline is known.
