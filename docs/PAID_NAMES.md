# Paid MineMine names and collision policy

Research checked 2026-11-02. Product intent: a player using the conventional email/passkey signup path pays **$2 USD for the account and the first year of its `username.minemine.eth` reservation**, with renewal afterward. The project owner reports owning `minemine.eth` and chose a **MineMine-managed ENS subname** pointing to the player's ZeroDev wallet. There is no separate account fee. An existing-wallet player can instead sign in with a wallet and choose an ENS name they currently own. The local name registry and wallet-selected full ENS display names are implemented; no paid checkout or ENS subname issuance is live yet.

## The one-name rule

Keep **one authoritative MineMine handle registry** for both signup paths. Normalize the requested bare handle before a hold or claim; the proposed first version accepts lowercase ASCII letters followed by 2–15 lowercase letters or digits (`^[a-z][a-z0-9]{2,15}$`). Case variants resolve to one handle. Reserve product/admin/system words. A handle is either available, held for a specific checkout until a short deadline, paid and bound to one account, claimed by a verified wallet user, or administratively reserved. A transaction must make the availability check and state change atomic. The stable Luanti character key remains the wallet-derived internal ID; a handle or ENS change cannot move another player's inventory or town.

An external-wallet player may display a **fully qualified, verified ENS name** such as `alice.eth`, even when another account has the MineMine handle `alice`; never silently shorten it to `alice`. If the wallet player requests the bare MineMine handle `alice`, it must pass the same registry check as a paid signup. In particular, `alice.minemine.eth` and a paid request for `alice` refer to the same `alice` namespace entry and cannot be assigned to different accounts. A reverse ENS name or address record is not ownership proof. Recheck current ownership when an ENS alias is bound and after transfers/expiry. A preexisting onchain record or owner for the exact `alice.minemine.eth` name also blocks a paid sale until its status is reconciled; the local registry cannot override ENS.

## What the $2 purchase must mean

An ENS subname can be either a project-managed record or a separately owned token. [ENSv2's subname guide](https://docs.ens.domains/ensv2/subnames/) explicitly distinguishes resolver records controlled by the parent from UserRegistry subname tokens with separate owners and roles. MineMine chose the **managed resolver-record** route: the player receives use of the name and its address record, while MineMine controls the record and the player does not receive a transferable subname token. [ENS says ENSv2 launched on mainnet on 2026-10-27](https://ens.domains/blog/post/ensv2-live-on-mainnet) and existing names can be migrated. A read-only `ENS_RPC_URL=https://ethereum-rpc.publicnode.com npm run ens:parent-check` on 2026-11-02 found active ENSv2 owner `0xE701998A8Fe6523b053DF9D9a2e300F7bb27E320` and expiry `2027-11-02T01:10:11Z`. Its resolver and subregistry were both the zero address. The current owner had `ROLE_SET_RESOLVER` and `ROLE_SET_SUBREGISTRY`. This means no managed `*.minemine.eth` resolver-record flow is configured yet. The read does **not** prove that the user controls that owner wallet, or that the future resolver will grant a safe operator permission to write records. The owner must sign in, attach a suitable resolver, and test managed records on a disposable parent before payment. Rerun the check with `ENS_EXPECTED_OWNER` set to the signing wallet address; a mismatch exits nonzero. The tool makes no transaction.

Point each managed name at its player's ZeroDev wallet and explain MineMine's record control in the purchase terms. Do not call a database hold “ENS ownership” or show `username.minemine.eth` as active until the authoritative ENS lookup resolves as intended. The $2 covers both signup and the first year of the managed name. Start the name term at verified onchain activation so delayed issuance does not shorten the buyer's year; explain that timing before payment and show the exact UTC expiration after activation. Renewal should require a separate, deliberate checkout unless the owner later approves automatic billing. The ZeroDev account remains accessible if its name term ends. Before charging, specify the renewal price, reminder timing, grace period, refund/dispute handling and how an expired onchain record is cleared before a handle can be reassigned. The parent ENS name must remain active throughout each sold term; the current observed parent expiry is not by itself enough to guarantee a full year for later purchases.

## Checkout and fulfillment sequence

1. Establish a recoverable ZeroDev account identity and its stable smart-wallet address. Reserve a unique handle with an account-bound checkout hold and a short payment-session lifetime. Check the exact ENS subname and parent permissions before offering payment. Admin reservations and verified ENS claims use the same collision check. Do not release the local hold merely because its timer elapsed; wait for a verified terminal payment-session status and reconcile delayed events first.
2. Create a server-priced **$2 USD, one-time** hosted Checkout Session for signup plus the first managed-name year, with an order ID bound to that hold and account. The browser cannot set the price, account ID or selected handle. MineMine never receives card numbers. A hold expires if payment is abandoned; it cannot be recycled while a payment may still complete without a reconciliation check. A later renewal is a distinct order; its price is still a product decision.
3. Fulfill only after a verified payment event. [Stripe's fulfillment guide](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page) requires server-side fulfillment and handling duplicate events; a success-page redirect is not proof of payment. Verify the webhook signature using the raw body, retrieve or validate the Checkout Session, require paid status and the exact `usd`/`200` amount, and atomically record the session/payment ID once. Handle delayed success, expiry, failure, duplicate delivery and out-of-order events.
4. Move the hold to a **paid reservation** bound to the account. Queue ENS issuance or record update, then verify the resulting name onchain before showing it as active. Keep an explicit `paid_pending_ens` state so an onchain or provider failure cannot be mistaken for completion. Retry safely or refund/offer a different name if fulfillment cannot succeed. Audit every transition and admin override.
5. Test two simultaneous checkouts for the same handle, payment after hold expiry, webhook replay, server restart/restore, ENS ownership transfer, parent expiry, ZeroDev recovery, chargebacks, and alias changes. The beta invite gate remains a separate requirement; the $2 purchase should not accidentally bypass a closed beta unless that is a deliberate policy.

[Stripe's current US standard pricing](https://stripe.com/pricing) lists 2.9% + 30¢ per successful domestic card payment. On a $2 charge that is about **36¢ in processing fees**, leaving about **$1.64 before ENS transaction gas, ZeroDev usage, taxes, refunds and disputes**. This is a feasibility estimate, not an approved profit margin or a guarantee of the final fee. The project's first VPS budget remains capped at $10/month; payment processing and ENS costs need their own test and budget decision. Use test-mode checkout and a disposable ENS test parent before any live purchase.

## Release gates

- `server/name-registry.mjs` now provides a private SQLite registry with normalized handle keys, admin reservations, account-bound checkout holds, idempotent paid transitions, explicit unpaid-hold release, verified-ENS claim storage and an audit trail. Tests cover cross-connection collisions, restart persistence, admin expiry and late-payment rejection; the local cold-backup test restores a paid-pending registry record. Admin wallet users can create and release seven-day local holds through authenticated routes. The registry is connected to verified full ENS display selection for wallet players, but **not connected** to paid signup, payment webhooks or subname issuance, so no player sale is available yet. The ENS claim method requires its caller to verify ownership first; the checkout release method requires provider-confirmed expiry/cancellation first. The database is stored in the world directory for stopped-world backup.
- A verified wallet selection of a direct `username.minemine.eth` name now checks the same registry before display. Admin reservations, checkout holds and ENS selections cannot assign that direct handle to different accounts, including across two SQLite connections. A reverse ENS name is subject to the same display check. This is a **local namespace safeguard**, not proof that a paid name can be issued: checkout still needs a fresh onchain record and parent-permission preflight, and onchain changes can race any local read.
- A separate managed-name path now supports the chosen resolver-record model: `paid_pending_ens` can become `paid_active` only after a mainnet resolver callback returns the account's exact wallet address. It preserves payment and order binding, is idempotent under webhook replay, and survives migration from the previous SQLite schema and a stopped-world backup. The identity API and native-ticket identity path re-resolve an active name on each use; a missing, changed or unavailable record hides the name while retaining the paid record. Activation is not wired to an ENS writer, and a mocked resolver does not prove that `minemine.eth` is configured or controlled. A real managed subname needs a disposable-parent write and readback before activation is trusted in production.
- `server/name-checkout.mjs` now has an **internal Stripe test-mode-only** Checkout creator and webhook fulfillment path. The server fixes the price at 200 USD cents, one card-only line item, account-bound order metadata and a 45-minute expiry; retries use the same order ID as Stripe's idempotency key. The raw-body webhook uses Stripe's official signature verifier, retrieves the session from Stripe, requires test mode, `paid`/`complete`, exact USD amount and line item, then atomically changes a matching hold to `paid_pending_ens`. A verified terminal `expired`/`unpaid` session releases its hold. Handler and service tests cover invalid signatures, wrong price, unpaid completion, duplicate delivery, collisions and late fulfillment after release. No public checkout creation route exists, and `readConfig` rejects live-mode keys; this is **not** a working player purchase. Before any sale, bind a real ZeroDev account, preflight ENS and parent permissions, settle terms, test with Stripe, and wire issuance/refunds/disputes.
- Verify the reported control of `minemine.eth` with the owner's wallet, including its current registry, migration state and permission to set managed subname records. No sale of `*.minemine.eth` before that proof.
- Implement the chosen one-year managed-name term, renewal checkout and expiry display; set the renewal price, reminder/grace/refund/dispute policy, and test actual mainnet gas and provider cost.
- Obtain and configure a payment-provider test account and ZeroDev test project. Keep keys server-side and out of the repository.
- Implement and test the shared registry, account binding, hosted checkout, verified idempotent fulfillment and onchain issuance. Show a clear pending state if ENS has not been issued yet.
