# SpacetimeDB scaling plan

Authentication research checked against the official SpacetimeDB docs on 2026-11-04. The isolated [profile module prototype](../spacetimedb/README.md) pins CLI and npm library 2.14.1, compiles locally, passes in-memory reducer tests, and published to a disposable loopback-only host that rejected an anonymous write with HTTP 403. Verified MineMine wallet sign-ins now queue durable source profiles, and a one-shot Node command projects them through confirmed HTTP reducer calls; its network path passed against a disposable loopback host. It is not scheduled or connected to a public database, and real OIDC service credentials remain untested. The official [2.11 security notice](https://spacetimedb.com/changelog/v2.11.0) is one reason the older local 2.4.1 CLI must not be used for a production host.

This is the **next phase**, not part of the currently playable game. The present Luanti server remains authoritative for voxel edits, inventory, physics, and town protection. Adding a database by itself will not raise the engine's player limit; first measure native-server step intervals, map emerge time, outbound bandwidth, reconnects, and memory with 16, then 32 and 64 clients. The [native load measurement plan](NATIVE_LOAD_METRICS.md) distinguishes sampled step intervals from CPU execution time.

The first opt-in 32-browser CI rehearsal [stopped at the 16th join](https://github.com/cupOJoseph/minemine/actions/runs/41894150488). Fifteen joined, but the remaining clients and a 32-online metrics window were never reached. The Luanti/Node service slice had no OOM events; browser resource use outside it was not captured. A corrected separate-pad [16-client run](https://github.com/cupOJoseph/minemine/actions/runs/41903857277) passed eight directed movements and reconnect. These results warrant independent-client and whole-VM measurements before assigning the join bottleneck to Luanti or designing a SpacetimeDB authority migration around it.

A [second opt-in 32-browser run](https://github.com/cupOJoseph/minemine/actions/runs/41911907967) was cancelled at the 50-minute workflow limit without retained logs or artifacts. The [bounded follow-up](https://github.com/cupOJoseph/minemine/actions/runs/41921691547) retained its partial data: 20 browsers completed native joins before the 25-minute deadline, while the 21st connected but had not joined. The Luanti/Node service slice stayed below 274 MB with zero OOM events and the browser runner still reported at least 5.68 GiB `MemAvailable`; join times nevertheless grew. That test did not reach 32 online, movement or reconnect, and does not prove a Luanti limit or a SpacetimeDB migration need. See the [measurement details](NATIVE_LOAD_METRICS.md).

An opt-in [20-client activity rehearsal](https://github.com/cupOJoseph/minemine/actions/runs/41927354406) subsequently passed two fresh 20-online windows, 7 of 8 directed movements, and 20 → 19 → 20 native presence on reconnect. The service slice had zero OOM events, but the separate browser runner fell to 1.00 GiB available memory. A parallel routine 16-client PR run passed eight movements but timed out waiting for one reconnect; that reliability failure remains under investigation. Neither run measured sustained voxel edits, independent client machines or a whole production VM, so the public alpha stays at two players and no world-authority migration is justified by these results alone.

An [exact-head rerun of that 16-client PR](https://github.com/cupOJoseph/minemine/actions/runs/41927329116/attempts/2) passed eight movements and 16 → 15 → 16 reconnect in 58.5 seconds. It establishes that the previous timeout did not reproduce on one immediate rerun; it does not identify its cause or prove longer-run reliability.

## A safe first integration

1. Start with a server-only integration. Keep the existing SIWE wallet proof at the web edge, add verified ZeroDev account binding before that signup path goes live, and let only a trusted Node/Luanti bridge call the first SpacetimeDB module using its own OIDC service credential. A durable wallet-profile outbox and one-shot bridge command are implemented, but a hosted database and real service credential are still required. Never send that credential to a browser. SpacetimeDB's [authentication guide](https://spacetimedb.com/docs/core-concepts/authentication/) documents service credentials; its [FAQ](https://spacetimedb.com/docs/intro/faq/) says database-issued development identities have no recovery if their token is lost. The existing Node in-memory session token is not an OIDC token.
2. Move a bounded social-data slice first: player public profile, town name/membership, or presence. Keep Luanti's world and inventory as the source of truth. Define one writer per field and a migration/backfill process; avoid an uncontrolled dual-write period. For every projected event, bind the wallet or smart-account address from the trusted server session rather than a browser-supplied reducer argument.
3. Add idempotent server-to-DB events for authoritative game changes. A Luanti mod or trusted bridge signs/authorizes these events; browser clients can subscribe to updates but cannot submit fabricated mining or block-edit events.
4. Model town claims as spatial records with owner, members, bounds, and revision. The payment entitlement still comes from confirmed on-chain reads. Reducers enforce ownership and non-overlap atomically. Only after the DB path passes the same protection and recovery tests should Luanti read decisions from it.
5. Before direct browser connections, select an OIDC issuer that gives each EOA or ZeroDev account a stable subject through reconnect and account recovery. The [SpacetimeDB auth-claims guide](https://spacetimedb.com/docs/core-concepts/authentication/usage/) says identity derives from issuer and subject, and warns that modules can receive valid tokens from other issuers unless they check both `iss` and `aud`. Reject a missing JWT, wrong issuer, wrong audience and a caller trying to mutate another account's row. Browser transports that cannot send a WebSocket `Authorization` header use the SDK's short-lived WebSocket-token exchange; do not persist that URL token in place of the underlying identity credential. Prove reconnect preserves the same account binding before exposing subscriptions or reducers to players.
6. Load-test with real browser clients and bot traffic. Measure p50/p95/p99 reducer latency, tick time, broadcast volume, subscription filtering, reconnect catch-up, and server cost. Decide whether a single world needs world partitioning, engine changes, or a different simulation architecture based on these measurements.

SpacetimeDB's module model uses [tables, reducers, and subscriptions](https://spacetimedb.com/docs/intro/key-architecture/). A database module is a possible authority for bounded social state; it does not make the current single Luanti simulation process support more players by itself.

## Pilot hosting within the budget

As checked on 2026-11-04, [Maincloud Free](https://spacetimedb.com/pricing) lists $0/month with 2,500 TeV of monthly credit (approximately 3 million function calls, 12.5 GB egress, or 1 GB table storage as individual equivalents). A separate SpacetimeDB pilot there would keep the proposed $7.80/month DigitalOcean base plan below the owner's $10 ceiling **only while usage remains within the free credit and before tax or VPS overages**. The $25/month Pro tier is outside that ceiling. Do not enable paid usage or move the live world into Maincloud without a cost and recovery decision. The free allowance is suitable to test low-frequency profile writes, not evidence that high-frequency movement or voxel edits for an MMO would fit; those require a measured cost forecast before an authority migration.

Maincloud Free [can pause an idle database](https://spacetimedb.com/docs/how-to/deploy/maincloud/); the pricing page lists automatic replication and backups under Pro. Keep the first module a disposable, server-only profile projection and measure actual energy, egress, reconnect catch-up, and availability before relying on it for player-visible state. Self-hosting SpacetimeDB alongside Luanti on the 1 GiB Droplet has not been measured and is not included in the first-host plan. A Maincloud account and OIDC service identity are still needed for a real bridge; the local pilot used neither.

## Acceptance gate for a single large world

A design is ready to replace a portion of Luanti authority only after two independent clients observe identical edits after reconnect, conflicting edits resolve deterministically, protection is enforced server-side, a forged caller identity and wrong-issuer/audience tokens are rejected, backups restore consistent world and account state, and a specified concurrency target holds acceptable tick and network latency on a named host. Until then, “many players in one world” remains a measured target, not a shipped feature.
