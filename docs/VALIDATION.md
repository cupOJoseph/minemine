## Local solo browser engines — 2026-10-23 EDT

The upgraded `21f97a29c16b` solo build ran from the local Node service at `http://127.0.0.1:42317/engine/index.html` on a 16 GB Apple M3 MacBook Air. The response supplied COOP/COEP, and both Playwright browsers reported a secure, cross-origin-isolated page with JSPI and WebGL 2. The tests used a 1280×800 viewport and a fresh automated browser context.

Playwright WebKit **27.2** rendered terrain, a held pickaxe, hearts and hotbar after the start click. Pressing **I** opened the crafting/inventory panel with starter items over the visible world. Its launcher labeled the world **temporary: storage unavailable** in this headless run, and the inventory run logged a pointer-lock focus error from automated input. This is evidence of rendering and one game UI interaction in Playwright WebKit; it does not establish saved-world persistence, all controls, a shipping Safari release, or multiplayer support. [WebKit's Safari 27 beta notes](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/) list JSPI support, which explains why testing an older Safari release would need its own compatibility check.

Playwright Firefox **157** loaded the WASM, reached the `Singleplayer` game title, created a 1280×800 canvas and logged the singleplayer join. The viewport remained black after more than 50 seconds, including a run that omitted the launcher's temporary WebGL-context teardown. The launcher also labeled storage temporary. The browser console logged failed `ws://.../worker.js` attempts; whether those attempts caused the black image is unknown. A headed Playwright attempt closed before a screenshot, so it did not resolve the distinction between a headless graphics limitation and a Firefox game incompatibility. Mozilla tracks [macOS headless WebGL regressions](https://bugzilla.mozilla.org/show_bug.cgi?id=2036597) and a [macOS Firefox/Emscripten black-canvas case](https://bugzilla.mozilla.org/show_bug.cgi?id=2034971); neither issue has been proven to be this build's cause. Do not mark Firefox gameplay as working from the feature checks or engine-start callback alone.

No public Safari/Firefox deployment was tested. The current public Pages bundle is older than this local candidate. Browser coverage still needs a normal interactive Firefox run, shipping Safari testing, persistence/reload, and the storage-lock case before general release.
