# Website world map research and delivery plan

Research checked 2026-11-02. This feature is planned for the **shared native world**, not each player's private solo browser world. A map should show explored terrain on a MineMine website page, with optional town boundaries and deliberately controlled player markers. It must never publish the world database, wallet grants, private town quotas, or unfiltered server files.

## Existing Luanti options

The [Luanti programs directory](https://docs.luanti.org/for-creators/programs-and-editors/#mapping) lists both [Minetest mapserver](https://github.com/minetest-mapserver/mapserver) and [minetestmapper](https://docs.luanti.org/for-server-hosts/minetestmapper/). Mapserver is the closest existing equivalent to a live Minecraft web map: its own [README](https://github.com/minetest-mapserver/mapserver/blob/master/readme.md) describes incremental terrain tiles, a browser UI, player/world statistics, POIs and SQLite or PostgreSQL map databases. The [companion mod](https://github.com/minetest-mapserver/mapserver_mod) can send player positions and server statistics, and supports hiding individual players from the map. The README's compatibility list is stale, naming Minetest 5.0; the official [v4.11.0 release](https://github.com/minetest-mapserver/mapserver/releases/tag/v4.11.0), published 2026-10-26, includes a Luanti 5.17.0 Docker update. This is encouraging for our pinned 5.16.1, but still requires a copied-world test. The release's Linux amd64 archive is SHA-256 `21ab70f77ce830e16e254c0a20cba46422ca254c46cdbe554a16141d93d9f869`, matching its published checksums. Mapserver is an additional Go service; the mod is optional for basic terrain.

The mapserver's [incremental-rendering design](https://github.com/minetest-mapserver/mapserver/blob/master/doc/incrementalrendering.md) tracks modified mapblocks using database `mtime` triggers and then refreshes tiles. Its [installation guide](https://github.com/minetest-mapserver/mapserver/blob/master/doc/install.md) instructs operators to back up the world before trying it. Test only on a copied small SQLite world first, inspect whether it changes the world schema, then verify Luanti still starts and edits the world after mapserver runs. Do not attach it to the production world until backup/restore, concurrent access and version compatibility pass.

The pinned v4.11.0 [SQLite query and trigger](https://github.com/minetest-mapserver/mapserver/blob/v4.11.0/db/sqlite/sql.go) have a concrete pagination defect: the trigger gives all writes within a second the same `mtime`, while the incremental query sorts by that value, limits the result, and asks for strictly greater timestamps on its next batch. The [render job](https://github.com/minetest-mapserver/mapserver/blob/v4.11.0/tilerendererjob/incremental.go) persists the last returned timestamp. A small SQLite reproduction in `test/mapserver-cursor.test.mjs` shows that 343 same-second writes with the configured 128-block fetch produce one batch and leave 215 invisible to later fetches. The retained native run logged 343 mapblocks written and one 128-block incremental batch; this defect can explain that observation. The run did not retain the copied SQLite database, so it does not prove that the gold edit had reached disk or that this was the sole cause of the unchanged tile. Do not increase the fetch limit and call live refresh fixed: a larger burst can still be skipped. Any repair needs lossless pagination, a stable write cutoff, restart recovery, and a copied-world live-edit test before the live map is enabled.

An experimental [pinned source patch](../patches/mapserver/001-bounded-cursor.patch) pages by timestamp plus mapblock position, persists that cursor after rendering, and waits until the current database timestamp has passed before reading a batch. In [native run 41508222192](https://github.com/cupOJoseph/minemine/actions/runs/41508222192), its fresh Go build and full upstream tests passed. On a copied Luanti world, it fetched 343 same-second mapblocks in three 128/128/87 batches. With Luanti and mapserver both running, a native gold-platform edit at (36, 143, 324) changed the served zoom-12 tile `0/12/1/-11.png` by the third two-second poll; the retained before/after PNGs show the new yellow platform. Luanti restarted cleanly on the copy. This proves that specific copied-world edit refreshed and the bounded burst did not skip rows. The patch is not in the public host archive or live map. A transaction that stamps a block before the cutoff and commits much later could still land behind the cursor; test or eliminate that case before claiming lossless updates. Measure concurrent Luanti/Node/Caddy/mapserver CPU, memory, tile storage, egress and game latency inside the 1 GiB/$10 host budget before exposing live tiles.

[Exact-head native run 41514443030](https://github.com/cupOJoseph/minemine/actions/runs/41514443030) repeated the patched 343-block burst and a real gold edit with the copied-world Luanti server, Node API and mapserver inside one **768 MiB, zero-swap systemd slice**. The API reported native/game readiness; tile `0/12/-7/-2.png` changed on the third poll. The slice peaked at **805,306,368 bytes, exactly its limit**. Its `memory.events` recorded `max 403`, `oom 0`, and `oom_kill 0`. The [Linux cgroup documentation](https://www.kernel.org/doc/html/v6.14/admin-guide/cgroup-v2.html#memory) defines `max` as an attempted crossing of the maximum boundary that can be recovered by reclaim. The test passed, but it has no measured service-memory headroom under this cap. It ran on a larger CI host; Caddy was not running, the OS and browsers were outside the slice, and CPU was not restricted to one vCPU. Keep the live map off the proposed 1 GiB host until a whole-VM test shows acceptable latency and memory headroom under longer player load. The bounded static `/map/` snapshot remains the viable current option.

The [mapserver sizing guide](https://github.com/minetest-mapserver/mapserver/blob/master/doc/recommended_specs.md) says historical worlds can consume several gigabytes of tile storage, rendering uses available CPU cores by default, and its comfortable example is 4+ cores, 8+ GiB RAM and 20+ GiB storage. It says one render job can run, more slowly. Those are upstream recommendations, not a measured MineMine requirement. The proposed MineMine alpha has **one shared vCPU, 1 GiB RAM and 25 GiB disk**, so a live map is a separate capacity gate, not part of the current $7.80/month host claim. The mapserver [code is MIT licensed, with separately attributed textures](https://github.com/minetest-mapserver/mapserver/blob/master/doc/license.md); review the exact release and assets before redistribution.

`minetestmapper` is a simpler fallback. The [Luanti server-host guide](https://docs.luanti.org/for-server-hosts/minetestmapper/) shows a top-down PNG export from an existing world, with one node per pixel and a configurable area. A static snapshot can be generated from a stopped-world backup or isolated world copy and served as a website image, with no live map process. It cannot, by itself, supply live player markers or dynamic zoomed tiles; town overlays would need our own read-only projection. Its runtime and storage costs also need measurement on the actual world.

## Decision sequence

1. **Define the first map:** explored terrain, pan/zoom, coordinates, spawn and town boundaries. Keep player-location sharing off until a visibility policy is chosen; public live positions can expose player activity. An opt-in or hide control must be enforced by the server, not just hidden in browser CSS.
2. **Spike mapserver on a copy:** [native run 41335040760](https://github.com/cupOJoseph/minemine/actions/runs/41335040760) passed a hash-locked v4.11.0 smoke on the pinned Luanti world: copied 4,063 generated mapblocks, loopback bind, one render job, 500-block cache, HTTP startup, and a served 256×256 PNG different from mapserver's blank response. The tile store was 18,195 bytes at the sampled point, the mapper installed two SQLite triggers on the copy, and Luanti restarted cleanly afterward. This establishes small-world startup and nonblank rendering compatibility. It does not establish that edits refresh correctly, that all map layers/coordinates render, or that Luanti and mapserver can run together under the $10 host limit. The earlier [run 41333998298](https://github.com/cupOJoseph/minemine/actions/runs/41333998298) saved a blank tile because the smoke confused disk path order with the API's `layer/x/y/zoom` order; the corrected check compares the actual HTTP response. Two follow-up CI runs kept mapserver and Luanti live on the copied world but did not refresh the selected zoom-12 tile within 90 seconds after a native edit. [Run 41379738262](https://github.com/cupOJoseph/minemine/actions/runs/41379738262) generated 343 mapblocks with its test platform; [run 41381094397](https://github.com/cupOJoseph/minemine/actions/runs/41381094397) edited an existing mapblock without increasing the block count. In both, the mapper logged one 128-block incremental batch and the saved before/after PNGs were byte-identical. This proves the tested live configuration is not yet correct. The pinned [SQLite query](https://github.com/minetest-mapserver/mapserver/blob/v4.11.0/db/sqlite/sql.go) has a reproducible same-second pagination defect, but the retained logs do not establish whether the gold edit itself reached disk or whether that defect alone caused the unchanged tile. The experiments were reverted from release CI after saving their logs; the prior nonblank-tile compatibility check remains. [Run 41383691000](https://github.com/cupOJoseph/minemine/actions/runs/41383691000) then built pinned minetestmapper commit `88c7381a20ada1992169522d590ebad36195507e`, copied the stopped native test world, and rendered a bounded 1024×1024, 38,611-byte PNG. The `/map/` page displays that snapshot with pan, zoom, signed X/Z coordinates, a generation time and an origin marker; desktop/mobile Chromium interaction, no horizontal overflow and no page errors passed, with screenshots retained. The Pages packager checks the image hash and dimensions. This is a test-world snapshot, not a live public shared-world map or a verified spawn point. Revisit live rendering only after edit refresh and CPU/RAM/disk impact pass under the whole-VM budget. Review the optional mod and its `secure.http_mods` / loopback secret before enabling live markers.
3. **Budget gate:** run Luanti, Node, Caddy and mapserver together inside a whole-VM-sized limit with a small map. If the map causes game lag, exhausts disk headroom or violates the $10/month cap, start with a bounded static minetestmapper snapshot; do not raise the VPS spend without the owner's approval. Record refresh interval and backup/restore behavior.
4. **Website integration:** serve the selected map under `/map/` on the MineMine origin, with a clear map freshness indicator. Expose only the map UI and sanitized tiles/data. The authoritative `town_claims` mod remains the source of truth for boundaries and membership; project its claims into read-only map shapes, never infer ownership from tile colors or a client request. Show the town name and protected x/z column footprint, not private quotas or wallet addresses. Test negative coordinates, overlapping/removed claims, large boundaries and reloading after world restart.
5. **Fallback if neither fits:** build a small tile/export pipeline from a consistent snapshot and a simple browser map viewer. Keep the renderer separate from the game process. Avoid writing a custom live world renderer until an existing tool has failed the compatibility or budget spike with recorded evidence.

**Current acceptance:** the local `/map/` page pans and zooms a dated test-world snapshot, reports signed coordinates and displays the paid nine-column Probe Town boundary. The [native overlay run](https://github.com/cupOJoseph/minemine/actions/runs/41386314237) passed its copied-world export and desktop/mobile Chromium checks. [Exact-head run 41387375708](https://github.com/cupOJoseph/minemine/actions/runs/41387375708) also matched the exported bounds to the paid claim’s recorded native X/Z position. The projection originates in `town_claims`, uses Luanti’s documented [atomic file write](https://github.com/luanti-org/luanti/blob/5.16.1/doc/lua_api.md), and excludes wallet IDs, membership, invitations and quotas. The image and claim metadata come from the same stopped-world copy; the public package validates the claim schema and image hash. [Native run 41486172060](https://github.com/cupOJoseph/minemine/actions/runs/41486172060) passed a second wallet’s paid nine-column claim at negative X/Z, removal from the public projection, relocation to X/Z −65 through −63, owner/outsider protection, native restart persistence, stopped-world export, desktop/mobile Chromium navigation and host map publication. The committed map has since been refreshed from [native run 41489035544](https://github.com/cupOJoseph/minemine/actions/runs/41489035544): 59,585 bytes at 1024×1024 with both paid claims and the default spawn at X −192, Z −192. Its PNG hash and metadata passed local Pages staging; desktop/mobile Chromium located the real spawn and negative claim. Overlap and large-boundary map behavior remain to be tested. Outside-network access, enabled refresh, production backup interaction and whole-VM CPU/RAM/disk/egress measurements remain. There are no live player markers. The image must stay labeled as a snapshot until those delivery gates pass.

**Host export candidate:** `scripts/publish-map-from-backup.mjs` reads a `backup-world.sh` archive and SHA-256 sidecar, checks SQLite integrity, renders with the pinned mapper included in the host archive, and atomically switches metadata after installing a content-hashed PNG. The page accepts only a filename matching that hash; [exact-head native CI 41476260034](https://github.com/cupOJoseph/minemine/actions/runs/41476260034) passed this path on a relocated host archive and a copied paid-town world: an 82,330-byte 1024×1024 image, one public town claim, and desktop/mobile Chromium loading of its versioned image. [Native run 41485197897](https://github.com/cupOJoseph/minemine/actions/runs/41485197897) passed the packaged `refresh-map-from-backup.mjs` against a copied-world archive, its second-run skip, and Chromium loading of the published image. The script selects the newest backup and avoids re-rendering the same archive; the packaged service/timer are opt-in only. The timer never creates a backup or interrupts the game. Whole-VM resource measurements, a cold-backup maintenance schedule, and public-host delivery remain before enabling it. See the [deployment steps](DEPLOYMENT.md#publish-a-bounded-website-map-from-a-stopped-world-backup).

**Default spawn projection:** the pinned Minetest Game [spawn API](https://github.com/luanti-org/minetest_game/blob/c42e4d0c0ff9d27ff7b9b308c3cfc14098dd3a0f/game_api.txt) chooses a default position for new players, unless engine/static spawn overrides it or another callback intercepts. `world_map_spawn` waits for a new player, checks that the selected position matches their actual new-player location, and writes only its X/Z coordinates to `world-map-spawn.json`. The stopped-world exporter validates that file and adds a `spawn` field to the map snapshot. The viewer draws a separate amber marker and locate control if it falls inside the bounded image; older worlds and engine fallback show no marker. A local desktop/mobile Chromium fixture passed the locate control. [Native run 41489035544](https://github.com/cupOJoseph/minemine/actions/runs/41489035544) passed two-wallet play, stopped-world export, Chromium map rendering and host-backup publication. Its retained `static-world-map.json` artifact records the actual default spawn at X −192, Z −192, inside the 1024×1024 bounded image, with no player identity. [Exact-head native run 41491145848](https://github.com/cupOJoseph/minemine/actions/runs/41491145848) passed the stricter Chromium assertion for the actual projected spawn in both the copied-world snapshot and verified-backup publication; its two-wallet game and host archive steps also passed. This is a default new-player location, not a live player marker or a promise that every respawn uses it (beds can override respawn).
